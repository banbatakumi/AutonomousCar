## 0. 要約と決定事項

v0.3 の設計思想は妥当であり、**大枠はそのまま採用する**。以下は変更しない。

- SYNC(2B) + TYPE + SEQ + LEN + PAYLOAD + CRC16 の可変長フレーム
- CRC-16/CCITT-FALSE (poly=0x1021, init=0xFFFF, 反転なし, xorout=0x0000)、検査値 `"123456789"` → `0x29B1`
- 全フィールド リトルエンディアン
- LiDAR を 1周12セクタに分割して送る方式
- `PING` / `PONG` による 4タイムスタンプ方式の時刻同期
- 設定は `CONFIG_SET` / `CONFIG_ACK` で個別 ID + ack、`applied` に実適用値を返す
- GPIO ハートビート方式の E-Stop
- 送信優先度 `PONG > TELEMETRY > LIDAR_SECTOR > CONFIG_ACK > LOG`
- **TYPE の方向規約: `0x01-0x0F` = STM32 → Pi、`0x10-0x1F` = Pi → STM32**

### 決定済み

| 項目 | 決定 |
|---|---|
| LiDAR の経路 | **STM32 経由**のまま実装する (Pi 直結にはしない) |
| ステアリング CALIB | **廃止**。`mode = 3` は予約とし、原点合わせは組み立て時の作業とする |
| 累積オドメトリ | **追加**する (`odom_dist[2] : i32×2`、前輪 FL/FR、0.1mm 単位) |
| `accel_z` | **追加**する |
| `TELEMETRY` | **LEN = 66**、フレーム 73B、50Hz で 3.65 kB/s |

## 1. 確定した車両構成

v0.3 §11「未確定事項」への回答を兼ねる。以下はすべて実機で確定している事実である。

### 1.1 アクチュエータ

| 対象 | 構成 |
|---|---|
| 後輪 左 / 右 | BLDC モータ + 自作 MD。**トルク (N·m) モード**で駆動 |
| ステアリング | BLDC モータ + 自作 MD。**位置 (rad) モード**で駆動 |

MD とは 250000 bps 8N1 の独自プロトコルで通信し、MD から以下が **11バイトの状態フレーム**で返る。
`TELEMETRY` に載せられるモータ関連の値はここが上限である。

| 項目 | 型・単位 |
|---|---|
| status | `u8` — bit3:過電流 bit2:過熱 bit1:電源電圧異常 bit0:動作中 |
| temperature | `u8` [degC] — **符号なし** |
| theta (機械角) | `u16` × 0.1 mrad |
| speed (角速度) | `i16` × 0.01 rad/s |
| iq (q軸電流) | `i16` × 1 mA — **双方向、制動時は負** |
| torque_limit echo | `u8` — 適用中のトルク上限 |

- **トルクの実測値は存在しない。** MD が返すのは `iq [mA]` のみ。N·m への換算には
  トルク定数 Kt が必要だが**未実測**。したがって `TELEMETRY` には
  「**STM32 が MD に出した指令トルク**」を載せる (TC 適用後の最終値)。これは実測ではないが、
  TC/TV のチューニングにはこちらの方が有用である。
- モータの最大トルクは 0.1557 N·m、ステアリングに掛けているトルク上限は 0.1 N·m。
  **値域は極めて小さい**ので、`i16` で 0.001 N·m 刻みにするとほぼ分解能が無くなる。
  **0.0001 N·m/LSB** を使うこと。

### 1.2 センサ

#### エンコーダ ★v0.3 の前提と大きく異なる

- **アナログ出力の絶対角エンコーダを、前輪の左右に装着している。**
- ADC で読む。+3.3V をフルスケールとして **1回転 (0〜2π rad) で電圧が線形に一周**する。
- **パルス積算 (tick) という概念が存在しない。** したがって v0.3 の
  `odom_ticks[2] : i32×2` は実装できない。累積走行距離 `odom_dist[2]` (0.1mm 単位) で代替する。
- **装着位置は前輪 = 非駆動輪**。これが車速の真値であり、後輪のスリップ率算出に使う。
- 後輪の回転は MD が返す機械角・角速度から得る。

**Pi 側が必ず知っておくべき制約:**

1. **★分解能が粗い。低速域では `wheel_speed[FL,FR]` を使わないこと。**
   12bit ADC で 1回転 (2π) を測るため 1LSB = 1.53 mrad、これを制御周期 500us で微分すると
   **1LSB あたり 3.07 rad/s (= 0.092 m/s)** に化ける。実測でアナログ出力には ±100mV 程度の
   ノイズが乗っており、**生値のままだと静止中でも ±12 m/s 振れる** (2026-08-08 実測。
   静止20秒で 72% のサンプルが ±12 m/s、最大15サンプル連続)。
   - STM32 側は 4輪とも**帯域およそ 1.6Hz のローパス後**の値を送っている
     (2026-08-08 修正。それ以前は前輪だけ生値を送っており使い物にならなかった)。
   - **Pi 側でこの値を微分して加速度を求めてはならない** (加速度は IMU から取ること)。
   - 車体速度は `speed` を使うこと (同じフィルタが掛かっており、実測で静止時 ±0.026 m/s)。
   - **輪ごとの量が要るなら `odom_dist` の差分**を取ること (実測で静止20秒の変化が
     +0.8mm / 0.0mm と正常)。積算値なので微分ノイズが乗らない。
2. **前輪は操舵輪である。** §4.3 の射影の注意を必ず読むこと。
3. 絶対角のアンラップにより前進/後退の符号は出せるが、静止付近ではノイズで符号がばたつく。

#### IMU

- **MPU6050 (6軸: ジャイロ + 加速度)** + Mahony 相補フィルタ。DATA_RDY 割り込み駆動。
- **地磁気センサが無い。** したがって **yaw の絶対方位は出せず、積分ドリフトする。**
  v0.3 が `yaw` そのものを送らず `yaw_rate` のみにしているのは正しい判断であり、そのまま維持する。
- pitch / roll は重力ベクトルで補正されるためドリフトしない。
- ジャイロバイアスは静止時に追従補正しており、キャリブレーション値は Flash に永続化している。

#### 超音波

- HC-SR04 系を前方・後方に1つずつ。ピン変化割り込みでエコーパルス幅を測る。
- 測距範囲 **2cm 〜 約4m**。最小測距が 2cm あるため「距離 0」は物理的に発生しない。
  → **`0` を「無効/範囲外」の意味に使って安全である。**
- 往復時間の制約から測距周期は前後交互で **実質 20Hz 程度が上限**。
  `TELEMETRY` の 50Hz に対して更新が遅いので、**Pi 側は同じ値が連続することを前提に扱うこと。**

#### LiDAR

- LD06。230400 bps の専用 UART で STM32 に接続。回転モータの PWM と電源スイッチも STM32 が持つ。
- STM32 側で **1° ビンにビニングして 360点 + 強度 360点**を保持している (実装済み)。
- LD06 の生出力は約 450点/周なので、1°ビンの時点で既に間引きが発生している。

### 1.3 電源 ★v0.3 の前提と異なる

**電源系統は2つある。**

| 系統 | 内容 | 電圧測定 | 電流測定 | 過電流閾値 |
|---|---|---|---|---|
| 駆動系 (Primary) | モータードライバ電源 | ✓ | ✓ | 5.0 A |
| シグナル系 (Secondary) | マイコン・Raspberry Pi・LiDAR・ライト類 | ✓ | ✓ | 3.0 A |

- どちらも **8セル ニッケル水素電池**。放電終止 8.0V (1.0V/cell)、満充電 11.2V (1.4V/cell)。
  低電圧警告は 8.0V 未満が 1秒継続、復帰は 8.8V (1.1V/cell、ヒステリシス付き)。
- したがって `batt_voltage` / `batt_current` は **各2つ必要**である。
- **電流センサは単方向 (INA180A2 + シャント、GND基準)。** 回生時に電流が逆流しても
  測定できず 0 に張り付く。`u8` で問題ない。
  ※ MD が返す `iq` は双方向なので、そちらは `i16` のままとする。この非対称は意図的である。
- **駆動系の過電流は DRIVE_POWER をハード遮断してラッチする。** リセットするまで復帰しない。
  → **Pi が `arm` を要求しても `armed` が立たない状態が正常に発生しうる。** これは異常ではない。

#### 温度センサ

| index | 対象 | 出所 | 精度 |
|---|---|---|---|
| 0 | MD 後左 | MD 状態フレーム `u8 [degC]` | 実用十分 |
| 1 | MD 後右 | 同上 | 実用十分 |
| 2 | MD ステア | 同上 | 実用十分 |
| 3 | STM32 | **MCU 内蔵温度センサ** | **工場較正なし、±10℃級の概算。ダイ温度であって基板温度ではない** |

index 3 は傾向監視にしか使えない。絶対値での閾値判定には使わないこと。

### 1.4 ステアリング ★重要

- 角度センサは **MD 内蔵のもの**であり、返るのは **モータの機械角** (0.1 mrad 分解能)。
- 直進中心点は「タイヤを手で真っ直ぐにしてボタンを押しながら起動」→ Flash に保存、という手順。
  **走行中にコマンドで実行するキャリブレーションシーケンスは存在しない** (v0.4 で CALIB モードを廃止)。
- 可動範囲はモータ角で ±60° にクランプしている。
- **モータ機械角から路面舵角への換算比 (リンク比) は未実測。**

**`steer_actual` / `target_steer` は「路面舵角」で定義する。** Pi 側の自転車モデルや
Pure Pursuit が必要とするのは路面舵角であり、STM32 側で換算して送受信する。

### 1.5 未実測のまま残っている量

### 確定した寸法 (2026-08-07 実測)

| 項目 | 値 |
|---|---|
| 車輪直径 (前後とも) | **60 mm** (半径 0.030 m) |
| ホイールベース | **230 mm** |
| トレッド | **155 mm** |
| 後輪の駆動方式 | **ダイレクトドライブ (減速比 1:1)** |

Pi 側の `config/vehicle.yaml` にこの値を入れてよい。ただし車輪半径は幾何寸法であり、
ゴムタイヤは荷重で潰れるぶん実際の転がり半径が数%小さくなる。この誤差は
**`speed` と `odom_dist` の倍率誤差にそのまま乗る**ため、走行距離の突き合わせで
Pi 側にスケール補正を持たせるか、STM32 側の定数を実走行から逆算して詰めること。

### まだ未実測のもの

- **ステアリングのリンク比 (モータ角 → 路面舵角)**。現状 `STEERING_LINKAGE_RATIO = 1.0`
  の仮値のため、**`steer_actual` / `target_steer` は路面舵角として正しくない**
- **左右の符号** (モータ・エンコーダの取り付け向き)
- **モータのトルク定数 Kt** (`motor_current` から N·m を推定する場合に必要。
  `torque_cmd` は指令値なので影響しない)

## 2. v0.3 の内部不整合 (修正済みとして v0.4 に反映)

1. **§4 の一覧表で `TELEMETRY` の LEN が 47 のまま。** §5.3 と §7 は 53 / 60B。v0.2 の更新漏れ。
2. **§5.1 の「1°ビニング」と「`angle_start` は実測値を送る」は両立しない。**
   1°ビンに入れた時点で角度は 1° 格子に量子化されるため、`angle_start` に実測の精度は残らない。
   → **`angle_start` / `angle_step` を廃止**し、角度は `sector_idx * 30 + i` [degree] で
   一意に決まるものとする (§5)。
3. **セクタ内の各点の時刻が復元できない。** `t_start_us` だけではセクタの所要時間が分からず、
   前セクタとの差分に頼ることになるため、1セクタでもロスすると歪み補正が壊れる。
   → **`duration_us` を追加**する。
4. **min 採用のビニングは走査マッチングにバイアスを与える。**
   「同一ビンに複数点が入ったら最小距離を採用 (安全側)」は**衝突判定用としては正しい**が、
   地図生成用のデータを近距離側に系統的に歪ませると ICP / スキャンマッチングの精度が落ちる。
   → **安全用途の最短距離判定は STM32 内部で完結させ、Pi に送る点群はバイアスのない
   代表点 (ビン中心に最も近い点) とする。**

## 3. STM32 側の実装制約 (Pi 側が知っておくべき事項)

### 3.1 `t_us` は起動からの経過時間、71.6 分でラップ

現ファームには monotonic な μs カウンタが存在しないため新規に実装する
(現行のタイマは 180MHz のサイクルカウンタベースで **約24秒でラップ**してしまう)。
新カウンタは **32bit μs、起動時 0 スタート、約 71.6 分でラップ**とする。
Pi 側は v0.3 §6.3-4 のとおり、差分を必ず符号なし演算で取ること。

### 3.2 ボーレート誤差は 0%

250000 bps は APB1 (45MHz) で USARTDIV = 11.25、APB2 (90MHz) で 22.5。
いずれも 1/16 刻みで**厳密に表現できるため誤差 0%**。フレーミングエラーの懸念は無い。

### 3.3 E-Stop ハートビート 【実装済み】

STM32 の EXTI はライン番号ごとに 1ポートしか選べない。Pi 連携用信号線 (PB12) と
前方超音波の ECHO (PA12) が同じ EXTI ライン 12 を使うため、**ハートビートを外部割り込みで
取ることはできない**。100Hz 矩形波 (エッジ間隔 5ms) を 2kHz の制御ループでポーリングしている。
50ms の途絶判定には十分間に合う。**Pi 側の実装に変更は不要。**

STM32 側の挙動を確定させたので、Pi 側は以下を前提にしてよい。

| 項目 | 挙動 |
|---|---|
| 信号 | **100Hz の矩形波**。デューティは問わない (エッジの有無だけを見る) |
| 駆動方式 | **オープンドレインでよい。基板に外付けプルアップがある** |
| 接続判定 | **エッジを10回 (=50ms 分) 数えて初めて「Pi が繋がっている」とみなす。** 単発のノイズで接続済みと判定して直後に緊急停止へ落ちるのを防ぐため |
| 未接続時 | ハートビートを一度も見ていない間は緊急停止を発動しない (ベンチ確認のため)。**つまり Pi 側は「出し始めたら出し続ける」必要がある。途中でやめると緊急停止になる** |
| 途絶時 | 50ms でラッチし、`TELEMETRY.flags` bit3 `estop_active` が立つ |
| 復帰 | **自動復帰しない。** ハートビートが戻っている状態で車両側のボタン2を人間が押すまで解除されない |
| 発動時の動作 | 目標車速0で制動し、ハザードを点滅。**駆動電源は切らない** (切るとMDが制動をかけられず惰行して停止距離が伸びるため) |

**Pi 側の注意**: 緊急停止から復帰させるには人間が車両のボタンを押す必要があるため、
GUI に「E-STOP 発動中 — 車両のボタン2で解除してください」と明示すること。
`estop_active` が立っている間は `COMMAND` を送っても一切効かない。

### 3.4 時刻同期のタイムスタンプ取得タイミング

v0.3 §6 の理論は正しいが、実装で以下を守らないと精度が出ない。STM32 側で対応する。

- **`t_ping_rx_us` (T2) は UART の IDLE 割り込みで、PING 最終バイト到着の瞬間に取る。**
  メインループで取ると周期分のジッタがそのままオフセット推定のバイアスになる。
- **`t_pong_tx_us` (T3) は「送信キュー投入時」ではなく「実際に1バイト目が線に出た瞬間」に取る。**
  LiDAR セクタ 1個の送信には 3.04 ms かかるため、PONG がその後ろに並ぶと T3 以降に
  最大 3ms の非対称遅延が発生し、**4タイムスタンプ方式でも除去されずオフセットに
  最大 1.5ms のバイアスが乗る**。PONG は送信キューの先頭に割り込ませ、送信開始割り込みで
  タイムスタンプを確定させる。

### 3.5 ★送信キューの遅延は最大 3.04ms で有界である

Pi 側の提案 A の根拠に関わるため明記する。

送信優先度が `TELEMETRY > LIDAR_SECTOR` であり、かつ**送信中の DMA フレームは途中で
中断しない**ため、`TELEMETRY` が LiDAR に阻まれる最大待ち時間は
**送信中の1フレーム分 = 76B × 10bit ÷ 250kbps = 3.04 ms** である。
`PONG` が更に割り込む場合を足しても 4ms 程度。

**「LiDAR バーストで上りが数十ms滞留する」という状況は発生しない。**
2段階タイムアウトを採用する理由は滞留ではなく、**単発の CRC エラーや一時的なロスで
即座に FAULT に落とさないため**である。

```
                                                            合計 66 バイト
```

**フレーム長 = 66 + 7 = 73 バイト。50Hz で 3.65 kB/s。**

### 配列インデックスの規約

**全配列で共通に `FL → FR → RL → RR`、モータ系は `RL → RR → ST → (MCU)`** とする。

| index | `wheel_speed` | `odom_dist` | `motor_current` | `torque_cmd` | `temp` | `md_status` |
|---|---|---|---|---|---|---|
| 0 | 前左 (FL) | 前左 (FL) | 後左 (RL) | 後左 (RL) | MD 後左 | MD 後左 |
| 1 | 前右 (FR) | 前右 (FR) | 後右 (RR) | 後右 (RR) | MD 後右 | MD 後右 |
| 2 | 後左 (RL) | — | ステア (ST) | — | MD ステア | MD ステア |
| 3 | 後右 (RR) | — | — | — | STM32 (MCU) | — |

### 4.1 `flags` (u32) ビット定義

| bit | 名称 | 意味 |
|---|---|---|
| 0-1 | `mode` | STM32 が**実際に採用している**モード (0=DISARM / 1=MANUAL / 2=AUTO / **3=予約**) |
| 2 | `armed` | DRIVE_POWER 投入済み (モータ出力可能) |
| 3 | `estop_active` | ハートビート断で発動中 |
| 4 | `uart_timeout` | `COMMAND` 途絶で自動ブレーキ中 |
| 5 | `tc_active` | **トラクションコントロールが今まさに介入中** |
| 6 | `tv_active` | **トルクベクタリングが今まさに介入中** |
| 7 | `imu_ok` | IMU 正常 |
| 8 | `lidar_ok` | LD06 正常受信中 |
| 9 | — | 予約 (旧 `calib_running`) |
| 10 | `steer_center_valid` | ステアリング原点が Flash に保存されている (これが 0 なら走行禁止) |
| 11 | `fault_drive_overcurrent` | 駆動系過電流 → DRIVE_POWER 遮断。**ラッチ** |
| 12 | `fault_signal_overcurrent` | シグナル系過電流 → LiDAR/駆動電源を遮断。**ラッチ** |
| 13 | `fault_drive_undervoltage` | 駆動系バッテリー電圧低下。警告のみ、**電圧が戻れば自動クリア** |
| 14 | `fault_signal_undervoltage` | シグナル系バッテリー電圧低下。警告のみ、**自動クリア** |
| 15 | `drive_power_locked` | 過電流ラッチにより `arm` 要求を拒否中 |
| 16-31 | — | 予約 |

- bit5/6 は「有効/無効」ではなく「**今まさに介入しているか**」を返す。
- bit9 は CALIB 廃止に伴い予約。bit10 は旧 `calib_done` を改名したもので、
  **「今この起動で実行した」ではなく「Flash に有効な原点が保存されている」**という意味に変わった。
- bit11/12 は**リセットするまで消えない**。bit13/14 は電圧が復帰すると消える。
- **bit15 が立っている間、Pi が `arm` を要求しても bit2 は立たない。** 仕様であり FAULT 扱いにしないこと。

### 4.2 `md_status[i]` (u8) ビット定義

| bit | 名称 | 出所 |
|---|---|---|
| 0 | `running` | MD が停止モードでない |
| 1 | `voltage_out_of_range` | MD 側で電源電圧異常を検知 |
| 2 | `overheat` | MD 側で過熱を検知 |
| 3 | `overcurrent` | MD 側で過電流を検知 |
| 4 | `comm_ok` | **STM32 が付加**。直近 100ms で MD からの状態フレームを受信できている |
| 5 | `limit_synced` | **STM32 が付加**。MD が適用中のトルク上限が指令値と一致 |
| 6-7 | — | 予約 |

**bit4 (`comm_ok`) は必須である。** MD が死んで無言になると status は最後の値のまま固まるため、
これが無いと過去の正常値を見続けることになる。**`comm_ok = 0` のとき、そのモータに関する
`temp` / `motor_current` / `wheel_speed` / `torque_cmd` の値は信用してはならない。**

### 4.3 ★前輪データの射影に関する重要な注意

**`odom_dist[]` と `wheel_speed[FL], wheel_speed[FR]` は「その車輪自身の走行軌跡に沿った
距離・速度」であり、車体中心線方向の値ではない。** 前輪は操舵輪だからである。

自転車モデルにおいて、舵角 δ のとき前輪の走行距離は車体中心線距離の **1/cos(δ) 倍**になる。

| 舵角 δ | 過大評価される割合 |
|---|---|
| 10° | +1.5% |
| 30° | **+15.5%** |
| 60° | **+100%** |

**Pi 側でデッドレコニングに使うときは必ず `steer_actual` で射影すること:**

```
d_center ≈ (odom_dist[FL] + odom_dist[FR]) / 2 × cos(steer_actual)
```

- 左右前輪は Ackermann により実際の舵角が異なる (δ_L ≠ δ_R) が、`steer_actual` は
  **自転車モデル等価の単一値**である。厳密解が必要なら車両幾何から δ_L / δ_R を復元すること。
- 左右差 `odom_dist[FR] − odom_dist[FL]` からヨー角変化を推定できるが、これも
  操舵輪であるため後輪差動の式は使えない。
- **一方 `speed` (車速) は STM32 側で車体中心線方向に射影済みの値として定義する。**
  射影が済んでいるのは `speed` だけである。

### 4.4 `odom_dist` のラップについて

**`i32` × 0.1mm のラップは ±214.7 km** である (2^31 × 10⁻⁴ m)。

```
2^32 × 0.1mm = 4.295×10^9 × 10^-4 m = 4.295×10^5 m = 429.5 km
```

※ Pi 側資料の「429m でラップ」は **1000倍の誤り**なので訂正すること。

ミニカーの走行距離ではラップに**到達しない**ため、`t_us` と異なり素直な符号付き減算で
問題ない。防御的に符号なし差分で扱うのは構わないが、`t_us` と同格の注意事項ではない。

### 4.5 設計上の補足

- **`speed` と `wheel_speed[4]` の両方を送る理由**: `speed` は車体中心線方向の車速、
  `wheel_speed` は各輪自身の周速。差分がそのままスリップ量になり、TC の挙動が GUI で直接見える。
  **どちらもローパス後の値**であり、生値ではない (§1.2)。

- **★台上 (ジャッキアップ) では閉ループ速度制御を検証できない。**
  前輪 (センシング) と後輪 (駆動) が機械的に切り離されるため、前輪を手で回すと
  「車体が前進している」と誤認して車速PIが**制動トルクを出す** (2026-08-08 実測: -0.0283 N·m)。
  これは仕様どおりの動作であり異常ではない。台上では `arm = 0` (DISARM) のまま観測すること。

- **★「車両が自分で駆動している」直接の証拠は `torque_cmd` だけである。**
  車輪速度・`odom_dist` は惰性・外力・手回しと区別がつかない。`wheel_speed` や `speed` で
  走行開始を判定すると、台上で前輪が自由に回るだけで誤検出する。
  補助的に使う場合は `md_status[].comm_ok` が立っていることを確認し、
  さらに一定時間 (150ms 程度) の継続を条件にすること
  (`comm_ok` が落ちている間の値は前回値の保持であって現在値ではない)。
- **`wheel_speed` を角速度 [rad/s] ではなく周速 [m/s] にする理由**: 車輪径やギア比を
  Pi が知らなくて済む。換算定数は STM32 側に閉じる。
- **`torque_cmd` を載せる理由**: TC が介入したのか単にトルクが足りないのかを切り分けるには、
  最終的に各輪へ何 N·m 出したかが見える必要がある。`flags` の `tc_active` と併せて見ると
  チューニングの効率が大きく変わる。
- **`odom_dist` を速度と別に送る理由**: 速度だけだと**パケットロスした分の移動距離が
  永久に失われる**。累積値なら次のパケットに正しい総距離が入っているのでロスに強い。

## 5. LiDAR パケット

### 5.1 `LIDAR_SECTOR` (0x01) — LEN = 69 【既定】

`angle_start` / `angle_step` を廃止し、`duration_us` / `rot_speed_dps` に置き換える。
**バイト数は v0.3 から変わらない。**

```
off  size  type     field            単位 / 備考
──────────────────────────────────────────────────────────────────────────────
  0    1   u8       sector_idx       0-11
  1    4   u32      t_start_us       このセクタ先頭点の取得時刻 (STM32 monotonic μs)
  5    2   u16      duration_us      先頭点から末尾点までの所要時間 ★新規
  7    2   u16      rot_speed_dps    ★1 deg/s★ LD06 が報告する回転速度 ★新規
  9   60   u16×30   dist[30]         mm。0 = 無効 / 範囲外
──────────────────────────────────────────────────────────────────────────────
                                                            合計 69 バイト
```

- **角度は `sector_idx * 30 + i` [degree] で一意に決まる** (1°ビン固定)。実測角度は送らない。
- `t_start_us` と `duration_us` から各点の時刻を線形補間できる。
  **セクタを1つロスしても歪み補正が壊れない**のがこの変更の目的。
  なお `duration_us` はセクタ内の**先頭点から末尾点まで**であり、30点ぶんの区間 (29間隔)
  である点に注意 (1点ぶん短い)。
- **★訂正: `rot_speed_dps` の単位は `0.01 deg/s` ではなく `1 deg/s`。**
  LD06 は 10Hz 回転で **3600 deg/s** 出るため、0.01 単位では u16 の上限 (655.35 deg/s) を
  6倍近く超えて桁あふれする。1 deg/s なら 65535 まで表現でき、3600 に対する分解能も 0.03% で十分。
- `rot_speed_dps` は回転異常の検出と、補間の妥当性チェックに使う。

### 5.2 `LIDAR_SECTOR_I` (0x05) — LEN = 99

`LIDAR_SECTOR` と同一レイアウトの末尾に `intensity[30] : u8×30` を追加。
LD06 の信頼度をそのまま転送する。

### 5.3 `LIDAR_SECTOR_C` (0x09) — LEN = 39 【新規・圧縮版】

帯域が逼迫した場合の逃げ道。**`0x01` と同一レイアウトで距離のみ 1バイト化**する。

```
off  size  type     field            単位 / 備考
──────────────────────────────────────────────────────────────────────────────
  0    1   u8       sector_idx       0-11
  1    4   u32      t_start_us
  5    2   u16      duration_us
  7    2   u16      rot_speed_dps
  9   30   u8×30    dist[30]         2 cm/LSB。0 = 無効、255 = 5.10m 以上 (飽和)
──────────────────────────────────────────────────────────────────────────────
                                                            合計 39 バイト
```

- **`255` は「5.10m ちょうど」ではなく「5.10m 以上 (飽和)」である。** 地図生成では
  「少なくともこの距離以上に障害物が無い」として扱い、点として打たないこと。
- LD06 の測距精度が ±1.5cm 程度であるため、**2cm 量子化による情報損失はほぼ無い**。
  失われるのは 5.1m 以遠の情報だけである。
- **9.12 kB/s → 5.52 kB/s** に削減できる。

**専用 TYPE を割り当てる理由 (Pi 側提案 D を採用)**: 同一 TYPE で LEN が変わると、
エラー処理の「`LEN` が TYPE の期待値と不一致なら破棄」というルールと衝突するため。

### 5.4 出力フォーマットの切り替え

**`param_id 0x0040` を bool ではなく enum とする**（v0.3 の「LiDAR 強度送信 有効」を置き換え）。

| 値 | 送信される TYPE | 帯域 |
|---|---|---|
| **0 (既定)** | `0x01` LIDAR_SECTOR | 9.12 kB/s |
| 1 | `0x05` LIDAR_SECTOR_I | 12.7 kB/s |
| 2 | `0x09` LIDAR_SECTOR_C | 5.52 kB/s |

bool を2本 (強度 on/off + 圧縮 on/off) にしないのは、**「圧縮 かつ 強度付き」という
第4の組み合わせが表現できてしまい、未実装のまま指定される余地が残るため**。
`param_id 0x0041` は使用しない (予約)。

## 6. `COMMAND` (0x10) — LEN = 10

レイアウトは v0.3 のまま。以下の定義を確定させる。

- **`target_steer` は路面舵角 [0.0001 rad]、反時計回り正 (左旋回)。** モータ角ではない。
- **`mode = 3` は予約。** CALIB は廃止したため Pi 側の状態機械からも削除済み。
  STM32 は `mode = 3` を受信したら現在のモードを維持し、`flags` bit0-1 には
  実際に採用しているモードを返す。
- **`COMMAND` 途絶のタイムアウトは 100ms** (v0.3 の 200ms から短縮)。
  100Hz 送信に対して 200ms は 20発の取りこぼしを許すことになり緩すぎる。
  3 m/s なら 60cm 進んでからブレーキがかかる。

## 7. 追加パケット 【確定】

### 7.1 `VERSION` (0x07, STM32 → Pi) — LEN = 10 / `VERSION_REQ` (0x14, Pi → STM32) — LEN = 0

```
VERSION     : [protocol_version : u16][fw_id : u32][build_epoch : u32]  = 10 B
VERSION_REQ : (ペイロード無し)                                          =  0 B
```

- **要求側に別 TYPE `0x14` を割り当てる。** Pi 側提案 B は要求も `0x07` (LEN=0) と
  していたが、これは**提案 D で挙げた「同一 TYPE で LEN が変わる問題」を自ら踏む**。
  加えて v0.3 の「`0x01-0x0F` = STM32→Pi / `0x10+` = Pi→STM32」という方向規約も崩れ、
  ロジックアナライザでの切り分けが難しくなる。
- STM32 は起動後 **100ms 間隔で3回**、`VERSION` を自発送信する。
- **Pi 側はリンク確立時に必ず `VERSION_REQ` を送ること。** 自発送信は Pi が
  起動していなければ無駄になるため、あくまで補助である。
- `protocol_version` は本仕様のバージョン (v0.4 → `0x0004`)。不一致なら Pi 側で FAULT。

### 7.2 `STATS` (0x08, STM32 → Pi) — LEN = 48、1Hz

**★Pi 側提案 C とは逆に、増分ではなく累積 `u32` とする。**

```
off  size  type     field               備考
──────────────────────────────────────────────────────────────────────────────
  0    4   u32      t_us                このスナップショットの時刻
  4    4   u32      rx_frame_ok         Pi → STM32 で正常受理したフレーム数
  8    4   u32      rx_crc_error        CRC 不一致で破棄した数
 12    4   u32      rx_len_error        LEN が TYPE の期待値と不一致
 16    4   u32      rx_unknown_type     未知の TYPE
 20    4   u32      tx_drop             送信キュー溢れで破棄した数 (主に LOG)
 24   12   u32×3    md_rx_count[3]      MD 状態フレームの正常受信数 [RL, RR, ST]
 36   12   u32×3    md_rx_error[3]      MD 状態フレームの CRC 不一致数 [RL, RR, ST]
──────────────────────────────────────────────────────────────────────────────
                                                            合計 48 バイト
```

**累積にする理由**: 増分方式は **`STATS` が1個ロスするとその1秒分のエラー件数が
永久に失われる**。これは `odom_dist` を速度と別に累積で送るのとまったく同じ理屈である。
累積値なら次のパケットに正しい総数が入っているためロスに強い。

「`u16` のラップを考えずに済む」という提案 C の目的は、**増分にすることではなく
`u32` にすること**で達成される。`u32` は 1000件/s でも 49日かかるため実質ラップしない。

**GUI 側は連続する2つの `STATS` の差を `t_us` の差で割ればレートが出る。**
途中でロスがあっても、平均レートとしては正しい値が得られる。

### 7.3 `CONFIG_GET` (0x13, Pi → STM32) — LEN = 2

```
CONFIG_GET : [param_id : u16] = 2 B
```

応答は `CONFIG_ACK` (0x03) をそのまま使う。`applied` に現在値、`result` は §5.6 と同じ。
**GUI 起動時に実機の現在値を同期するために必須**である
(`CONFIG_ACK` は書いたときしか返らないため)。

### 7.4 `LOG` (0x04) の変更

**先頭に `severity : u8` を 1バイト追加する。**

| 値 | 意味 |
|---|---|
| 0 | DEBUG |
| 1 | INFO |
| 2 | WARN |
| 3 | ERROR |

Pi 側でフィルタできないと実用にならない。以降のバイトは ASCII 文字列 (改行なし)。

## 8. エラー処理 (v0.3 §8 からの変更点)

| 事象 | 対応 |
|---|---|
| `COMMAND` が **100ms** 途絶 | **STM32 → 自動ブレーキ**、`flags.uart_timeout` を立てる |
| `TELEMETRY` が **100ms** 途絶 | **Pi → DEGRADED** (警告のみ、走行は継続) |
| `TELEMETRY` が **200ms** 途絶 | **Pi → FAULT** |

**上下で非対称にする理由**: 上りが LiDAR バーストで滞留するからではない (§3.5 のとおり
最大待ち時間は 3.04ms で有界)。**単発の CRC エラーや一時的なロスで即座に FAULT に
落とさないため**の2段構えである。下りの `COMMAND` は安全に直結するため一段で厳しくする。

その他 (CRC 不一致 → 破棄して次の SYNC を探す、SEQ 欠番でロス計上、等) は v0.3 のまま。

**まずは 52% のまま実装し、実測でロスが出たら `0x09` に切り替える**方針とする。
切替は `CONFIG_SET` で走行中でも可能なので、GUI から試せるようにしておくこと。

| `0x11` | `CONFIG_SET` | Pi → STM32 | イベント | 6 |
| `0x12` | `PING` | Pi → STM32 | 5 Hz | 4 |
| `0x13` | `CONFIG_GET` | Pi → STM32 | イベント | **2** |
| `0x14` | `VERSION_REQ` | Pi → STM32 | リンク確立時 | **0** |

**LEN は TYPE ごとに一意である** (方向規約により、受信側から見て曖昧さは生じない)。

## 11. 実装上の細かい注意

- **ペイロードはフレーム先頭から 5バイト目に始まるため、`u32` / `i32` が 4バイト境界に乗らない。**
  構造体を丸ごと `memcpy` する場合は `__packed` を付けるか、フィールド単位で組み立てること
  (非 packed 構造体へのキャストは未定義動作)。
- `SEQ` は送信方向ごとに 1本の通し番号とする。これは**リンク全体のロス率の指標**であり、
  「どのストリームが落ちたか」は分からない。LiDAR は `sector_idx` の連続性で追えるため実害は小さい。
- **`CONFIG_SET` の Flash 永続化は行わない (揮発)。** STM32 側は既に Flash を使っているが
  (ステアリング原点、IMU キャリブレーション)、暗黙に毎回書き込むのは書き換え寿命の点で避ける。
  永続化が必要になったら `CONFIG_SAVE` を別コマンドとして追加する。
- MD との通信では別に CRC-8/AUTOSAR を使っているが、これは STM32 内部で閉じており
  Pi 側とは無関係である。
